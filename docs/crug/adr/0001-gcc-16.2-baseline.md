# ADR 0001 - GCC 16.2 baseline and build environment

- **Status:** Accepted (2026-10-18)
- **Ratified:** 2026-10-18 by CLEG0078 (project owner)
- **Date:** 2026-10-18
- **Deciders:** project owner (ratification), build/release owner
- **Context doc:** MASTER_SPEC sections 5, 27, 31; ROADMAP phase 0 (L244-300); EXIT-GATES phase 0

## Context

The roadmap makes "a reproducible host and a pinned upstream" the first phase, and
phase 0 cannot close without an artefact that names the exact GCC release, its
checksum, the host packages and the target triples. Nothing in the four
specification documents named a version, so any gate that says "GCC is available"
could be satisfied by any compiler on any machine. This ADR records the pin as a
decision rather than as build notes, because every later claim about C semantics,
diagnostics and ABI is relative to this one release.

The baseline was published on 2026-08-07 and is a real release, not a future one
(gcc.gnu.org/releases.html).

## Decision

**D1 - The pin.** Crug is a fork of GCC 16.2.0 (tarball `gcc-16.2.0.tar.xz`,
102 MiB, SHA512 pinned in `docs/crug/gcc-baseline.sha512`). The full record -
download command, GPG verification, host prerequisites, configure line, target
triples and the update policy - is `docs/crug/GCC-BASELINE.md`. This ADR makes
that document citable; it does not duplicate the checksum, so the two cannot drift.
The tarball tree itself is imported into this repository (repository root is the
GCC top level; the compiler is `gcc/`) and the import commit carries the
annotated tag `releases/gcc-16.2`, which is the fork base every later change is
diffed against.

**D2 - What the pin governs.** Source compatibility claims (RFC-0001 section 1 on
uppercase normativity and section 7 conformance classes), the C and GNU C
regression suites used by phases 1 and 3, the diagnostic text compared by phase 20,
and the ABI claims of RFC-0001 section 22 are all relative to GCC 16.2.0.
Replacing the baseline requires a new ADR, not an edit.

**D3 - Configure and build.** `--enable-languages=c,c++ --disable-bootstrap
--enable-checking=yes --with-arch=x86-64 --with-tune=generic`, prefix
`/opt/crug`, out-of-tree build directory, host toolchain per the baseline
document. `--disable-multilib` because CRUG targets one triple per build and the
host has no 32-bit development libraries (configure otherwise fails its multilib
probe). `--enable-checking=yes` is required while the frontend assertions are
still being written, so a miscompile is caught as an ICE rather than as wrong code.

**D4 - Targets.** `x86_64-pc-linux-gnu` is primary and is the only target a
phase gate may use before phase 8. `aarch64-linux-gnu` becomes secondary at
phase 8. Kernel targets (x86_64 and aarch64) are phase 19; the kernel baseline is
pinned separately in `docs/crug/KERNEL-BASELINE.md` (Linux 6.18.57 LTS, tag
`v6.18.57`, commit `2ff600d29ee478d0a8d46ef8a58afb5e038fe692`,
`x86_64_defconfig`), which resolved conflict C-09 on 2026-10-18. The per-object
corpus is still missing, so shell class K0, and phase 19, remain unclaimable.

**D5 - Reproducibility evidence.** A phase-0 claim consists of the pinned checksum
passing, a build completing at a recorded commit, the tree under `gcc/` unchanged
since `releases/gcc-16.2`, and the phase-0 gate log archived under
`docs/crug/gates/phase-0/` by `scripts/gate.sh`. A build that cannot show all
four is not a phase-0 completion.

**Forbids.** An unpinned GCC (a distro package, a git checkout of `master`, a
"latest stable" alias); a bootstrap build as the gate build; a host dependence
that is not listed in the baseline document; claiming phase 0 from the output of
`gcc -v` alone.

## Consequences

- Phase 0's first CHECK reads the baseline document and verifies the tarball
  checksum, so the gate fails if either is missing.
- The baseline is a maintenance obligation: every upstream point release is a
  candidate for a new ADR, and the update procedure lives in the baseline document
  rather than being re-decided per build.
- Host prerequisites (GMP, MPFR, MPC, isl, zstd, python, flex, bison) become part of
  the developer onboarding path and may be asserted by a gate.

## Rejected alternatives

- **Track GCC `master`.** No reproducibility, no stable diagnostics for phase 20,
  and the C frontend's internal interfaces change without notice.
- **Build on the distro's GCC 13/14.** Nothing in the plan targets an older
  frontend, and the work in phases 4-16 assumes the 16.x internal API.
- **Record the checksum here instead of in one place.** Two files that must agree
  will eventually disagree; the gate reads the single source.
- **Import the tarball without a tag.** Phase 0's fourth check diffs `gcc/`
  against `releases/gcc-16.2`; without the tag the check has no referent, and a
  later edit inside `gcc/` would be indistinguishable from the import itself.

## Open questions

1. **Bootstrap build.** Stay with `--disable-bootstrap` for gates, or add a
   separate bootstrap pipeline before 1.0? **Recommended:** keep
   `--disable-bootstrap` for gates and add bootstrap to the release pipeline.
2. **Second host architecture.** Is an aarch64 host (not just target) required
   before phase 8? **Recommended:** no, cross-compilation from x86_64 suffices until
   the runtime phases.
3. **Point releases.** Does a GCC 16.2.x update need a new ADR? **Recommended:** yes
   for 16.3 and later; patch-level rebuilds inside 16.2.x are recorded in the
   baseline document.
