# ADR 0028 - TSan scope: the fiber-switch exception for Phase 22

- **Status:** Proposed
- **Date:** 2026-10-20
- **Deciders:** project owner (the sanitizer policy and the Phase 22 exception),
  runtime maintainer (the context switch and the PAL wait path)
- **Relates:** ADR 0009 (scheduler model), ADR 0011 (PAL contract), ADR 0013
  (architecture context switch), ADR 0025 (channels and select),
  `docs/crug/EXIT-GATES.md` Phase 22, `docs/crug/RELEASE-POLICY.md` section
  3.2, `scripts/check-sanitizer.sh`, `scripts/check-tasks-sanitizer.sh`

## Context

The Phase 22 gate ("Security and Reliability Qualification" in
`docs/crug/EXIT-GATES.md`) requires ASan, UBSan and LeakSanitizer over the
task, scope and channel suites and a TSan arm, and Release Policy section 3.2
already states the rule this ADR has to make precise: "the v1 context switch is
not annotated with TSan's fiber API, so TSan is applied only where no stack
switch occurs."

ThreadSanitizer models happens-before between **OS threads**. When execution
moves to another stack by hand, TSan must be told: the stack is registered with
`__tsan_create_fiber`, and every switch calls `__tsan_switch_to_fiber` so the
tool can move its shadow state and its thread identity with the execution. The
v1 runtime does neither. `crug_ctx_switch` in
`libcrug/arch/x86_64/sysv/switch.S` stores `%rsp` through `save_sp`, loads
`new_sp`, pops the callee-saved registers and returns into the other task; the
only appearance of the word "fiber" under `libcrug/` is the comment in
`libcrug/core/task.h`. There is no TSan call in the runtime, and none is
possible without either linking the TSan runtime into every build or guarding
the symbols.

Running TSan over that switch anyway would produce two kinds of wrong answer.
It reports false positives when it cannot unwind a stack it did not create. More
importantly it produces false negatives: accesses made on a task stack are
attributed to the worker thread that happens to be running, the happens-before
edges between two tasks do not exist in its model, and "TSan clean" would then
assert something the tool never checked. A gate line that can pass for the wrong
reason is worse than an explicit exception.

## Decision

### D1 - TSan is applied only where no fiber switch occurs

The scheduler, scope and task paths are **not** TSan arms. They stay covered by
ASan + UBSan + LeakSanitizer: `scripts/check-tasks-sanitizer.sh` runs the task
suite, the 100000-task stress and the 3000-task/200-scope stress, and
`scripts/check-sanitizer.sh` adds the channel tests (`chan_basic`,
`chan_select`, and `chan_handoff`, which spawns tasks) plus an OS-thread channel
and PAL stress program. All of those run under
`-fsanitize=address,undefined` with `-fno-omit-frame-pointer`.

The TSan arm is the OS-thread channel exchange, which never calls
`crug_ctx_switch`: four producer OS threads created with
`crug_pal_thread_create` and the main thread as receiver exchange 800 tagged
`uint64_t` values through one capacity-4 channel, so the blocking send and
receive paths run `chan_idle`'s PAL wait and wake (the futex path of
`libcrug/pal/linux/pal_linux.c`) rather than a task yield. The program is
generated by `scripts/check-sanitizer.sh` into `build/sanitizer/san_stress.c`,
built with `clang -fsanitize=thread -DCRUG_TSAN_ARM`, and run with
`TSAN_OPTIONS=` (empty). The arm checks: every value arrives once and in order,
the channel drains, `sent == received == 800`, `created == live`, close is
idempotent, a closed receive yields the zero sentinel without incrementing
`received`, and joining/`crug_pal_shutdown` are clean. The `CRUG_TSAN_ARM`
define only omits the `mmap`/`mprotect` PAL checks, which are not part of the
race question and stay in the ASan arm.

The arm must not be made green by suppression. `scripts/check-sanitizer.sh`
sets `TSAN_OPTIONS=` rather than inheriting a suppression file, and treats a
non-zero exit or any `WARNING: ThreadSanitizer`, `ThreadSanitizer: data race`
or `SUMMARY: ThreadSanitizer` line as a report. `check-sanitizer.sh` prints
`sanitizer: ASan and UBSan clean over tasks/scopes/channels; TSan clean on the
OS-thread channel arm; fiber exception recorded in ADR 0028` and exits 0 only
when every arm is clean.

### D2 - The exception is one arm of Phase 22, and it expires

This is the Phase 22 exception named by the gate and by Release Policy 3.2. It
does not reduce the ASan/UBSan/LSan requirement anywhere, and it does not
license skipping TSan for other OS-thread code: any future runtime path that
creates OS threads and synchronizes through shared memory is TSan-eligible
without needing the fiber API.

A future fiber-hook increment must remove the exception, not widen it:

1. Guard the TSan fiber symbols (`__tsan_create_fiber`,
   `__tsan_destroy_fiber`, `__tsan_switch_to_fiber`) so a normal build links no
   TSan runtime, for example weak declarations plus a compile-time or
   weak-symbol check.
2. Register every task stack when the task is first scheduled and destroy the
   fiber when the task finishes, so TSan knows each task stack's extent.
3. Call `__tsan_switch_to_fiber (new_fiber, 0)` on both sides of the actual
   stack switch, including the return path to the worker, immediately around
   the `crug_ctx_switch` call rather than inside the assembly, and keep the
   calls off the non-TSan path.
4. Add a scheduler TSan arm to `scripts/check-sanitizer.sh` (for example the
   task stress and a channel handoff under TSan) and require it clean.
5. Delete or narrow this ADR and update the Phase 22 gate and Release Policy
   3.2 in the same change.

Until that lands, a TSan run over scheduler code is not evidence and must not be
cited in a gate archive, even if it happens to report clean.

### D3 - What the TSan arm does and does not cover

Covered by the OS-thread channel arm: the `chan.c` atomic lock, the `closed`
and slot-count transitions, the per-thread receive buffer, the channel
statistics atomics, the PAL futex wait/wake and thread create/join paths, and
the close/join ordering.

Not covered by TSan: data races on task stacks, task-to-task happens-before
across a manual switch, the scheduler's run queue and epoch word, and the scope
group state machine. Those are visible to ASan/UBSan only (memory errors and
undefined behaviour), not to a data-race detector. That gap is the reason this
ADR exists and the reason the fiber-hook increment is the exit condition.

One v1 API gap surfaced while building the arm: `chan_recv_common` keeps one
`malloc`'ed receive buffer per thread (`libcrug/core/chan.c`) and v1 has no
entry point that releases it, so a short-lived receiver OS thread leaves a
LeakSanitizer report at join. The arm therefore receives on the main thread,
whose buffer is still a live root at process exit; four producer threads only
send. A future increment that adds a receive-buffer release (or a per-channel
receive buffer) can extend the arm to receiver OS threads and add them to the
TSan coverage.

## Consequences

- The sanitizer suite is executable policy: `scripts/check-sanitizer.sh` is
  the single command behind the gate line, runs the task/scope suite first,
  then the channel tests and the ASan+UBSan stress program, then the TSan
  arm, and takes about four seconds on this host.
- A TSan report on a task/scope run is out of scope by this ADR, but a report
  on the OS-thread arm is a real defect and blocks the gate; no suppression is
  accepted, and narrowing the arm further (for example removing the futex
  producers) needs its own decision rather than a silent edit.
- The Phase 22 gate can be adjudicated: ASan/UBSan/LSan cover the scheduler,
  scopes and channels, and the data-race tool covers the part of the runtime
  that its model can actually see.
- The exception is a debt with a named owner and a named exit condition; the
  fiber-hook increment (D2) is the only way it is retired.

## Alternatives considered

- **Annotate the v1 switch now.** Rejected for Phase 22: it changes the hot
  switch path and its build, and it needs TSan runtime symbols in ordinary
  builds. The fiber-hook increment above is the reviewed shape for that work.
- **Run TSan over the scheduler and suppress the reports.** Rejected: a
  suppression file hides exactly the races the gate exists to find, and the
  resulting green line would not be reproducible by a reviewer.
- **Use ASan/UBSan only and drop the TSan requirement.** Rejected: Release
  Policy 3.2 and the Phase 22 gate require a data-race tool, and the OS-thread
  channel/PAL arm gives one honestly and cheaply.
- **Thread-per-task under TSan.** Rejected: it would test a different runtime
  model (no M:N scheduling, no manual stack switch) and would not exercise
  `chan.c` with the scheduler's task identities.
